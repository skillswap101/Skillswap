SkillSwap — FULL AUDIT FINDINGS

ARCHITECTURE
Current intended architecture:
Firebase Auth → Firebase UID → Supabase Third-Party Auth → Supabase PostgreSQL
Browser → Express API → Supabase service role

The architecture is valid, but the implementation is mixed/inconsistent.

============================================================
CRITICAL FINDINGS
============================================================

1. DATABASE SCHEMA DOES NOT MATCH APPLICATION CODE

- messages: database uses sender_id, receiver_id, created_at;
  application uses senderId, recipientId, createdAt, participantIds.

- sessions: database uses host_id, attendee_id, created_at;
  application uses mentorId, learnerId, participantIds, createdAt.

- proposals contains duplicated snake_case/camelCase fields such as
  sender_id/senderId and receiver_id/recipientId.

- reviews uses reviewer_id/reviewee_id while application uses
  camelCase-style objects.

ACTION:
Establish one authoritative schema and update application/database
consistently. Do not guess field mappings.

------------------------------------------------------------

2. ESCROW IS NOT ATOMIC

creditsService.ts performs SELECT balance → calculate → UPDATE for
proposal acceptance, escrow release, and refunds.

Concurrent requests can race.

ACTION:
Replace financial escrow mutations with PostgreSQL transactions/RPCs
using row locks.

------------------------------------------------------------

3. PAYMENT PERSISTENCE CAN FALL BACK TO MEMORY

paymentsService.ts can keep pending payments in an in-memory Map when
Supabase fails.

A Render restart can lose that state.

ACTION:
PostgreSQL must be authoritative. If database persistence fails,
fail the operation instead of silently using memory as authoritative
payment storage.

------------------------------------------------------------

4. FIREBASE → SUPABASE BRIDGE IS NOT FULLY VERIFIED

Supabase Third-Party Auth has Firebase project skillswapapp-905ca
registered.

The frontend still uses manual supabase.rest.headers.Authorization
mutation.

No setCustomUserClaims implementation was found.

ACTION:

- Verify Firebase tokens contain role=authenticated.
- Use Supabase's official accessToken callback pattern.
- Test Firebase login → token → Supabase → auth.uid() → RLS.
- Do not treat successful Firebase login alone as proof that Supabase
  RLS authentication works.

------------------------------------------------------------

5. USERS RLS CHANGE

The recent users_select_authenticated/users_insert_self/
users_update_self experiment was reversed.

Restored policies:

- Allow read users
- Allow upsert users

ACTION:
Do not change users RLS again until the Firebase/Supabase bridge is
verified.

------------------------------------------------------------

6. TEN RLS TABLES HAVE NO POLICIES

Supabase security advisor reports RLS enabled without policies on:

- escrowTransactions
- listings
- notifications
- pendingPayments
- pending_payments
- profiles
- stripe_events
- swaps
- transactions
- webrtcRooms

This is fail-closed, which is safer than public access, but features
may fail.

ACTION:
Inspect actual application usage and classify each table as:

- client-readable
- client-writable
- server-only
- obsolete
- duplicate

before adding policies.

------------------------------------------------------------

7. DUPLICATE PAYMENT TABLES

Both pendingPayments and pending_payments exist.

ACTION:
Choose one authoritative table after inspecting all references and
migrations. Migrate/remove the duplicate safely.

------------------------------------------------------------

8. DUPLICATE AUTHENTICATION MIDDLEWARE

There are two Firebase authentication paths:

- server.ts verifyFirebaseToken()
- middleware/auth.js authenticateUser()

Payment routes use the second.

ACTION:
Consolidate to one canonical Firebase Admin verification path.

------------------------------------------------------------

9. SERVER SUPABASE CREDENTIAL FALLBACKS

server/supabaseClient.ts has fallback paths involving anon/Vite
credentials.

ACTION:
Server-side Supabase client should use only:

SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY

and fail clearly if missing.

------------------------------------------------------------

10. FIREBASE CONFIGURATION FALLBACKS

src/firebase.ts contains fallback Firebase configuration.

ACTION:
Use environment configuration and fail clearly when required
production configuration is missing.

------------------------------------------------------------

11. PAYMENT SIMULATORS STILL EXIST

PayPal and M-Pesa contain simulator/test paths gated by NODE_ENV and
ALLOW_PAYMENT_SIMULATORS.

Production is currently protected by those gates.

ACTION:
Keep simulators out of production behaviour; eventually isolate/remove
them from production payment code.

------------------------------------------------------------

12. M-PESA OWNERSHIP CHECK

Payment status checks compare pending.userId with verified req.user.uid.

STATUS:
PASS.

------------------------------------------------------------

13. PAYPAL OWNERSHIP AND AMOUNT CHECKS

Capture verifies payment ownership and compares captured amount/currency
against the pending record.

STATUS:
PASS.

------------------------------------------------------------

14. STRIPE WEBHOOK

Stripe webhook signature verification exists.

STATUS:
PASS, assuming production webhook secret is configured correctly.

------------------------------------------------------------

15. PAYMENT ATOMIC RPC

fulfill_pending_payment exists and uses locking for payment fulfillment,
credit update, completion, and transaction logging.

STATUS:
GOOD.

However, duplicate function signatures exist and must be cleaned up
after inspection.

------------------------------------------------------------

16. ESCROW HAS NO EQUIVALENT ATOMIC FINANCIAL RPC

ACTION:
Add atomic PostgreSQL operations for:

- lock escrow credits
- release escrow credits
- refund escrow credits

------------------------------------------------------------

17. MOCK/DEMO DATA REMAINS

Mock-related runtime data and fallback/demo behaviour still exists in
parts of the repository.

ACTION:
Identify each occurrence and remove only where it can affect production
truth.

18. LOCAL STORAGE

ACTION:

- credits

Verify actual dashboard environment variables against what the server

22. RENDER ENVIRONMENT VARIABLES

render.yaml and server code expect different groups of variables.
