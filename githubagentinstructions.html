FINANCIAL SECURITY Treat the following as HIGH-RISK: - credits - escrow - balances - payments - transactions - refunds - payment completion Never trust client values for: balance credits escrow price amount payment status payment completion recipient sender transaction status Prices must come from a server-side package/catalog. Amounts must be validated server-side. --- 8. CREDIT SYSTEM The credit system must be server authoritative. Do not allow: browser → update balance The correct pattern is: payment ↓ verified payment ↓ atomic credit transaction ↓ credit ledger ↓ updated balance Create/use a proper ledger where appropriate. Every credit movement should have: - transaction ID - user ID - amount - direction - reason - source - reference - timestamp - idempotency information --- 9. ATOMIC PAYMENTS Inspect: paymentsService creditsService Stripe M-Pesa PayPal escrow session completion session cancellation proposal acceptance Look specifically for: read balance → calculate new balance → write balance without a database transaction or locking. These operations can race. Replace dangerous multi-step financial operations with atomic PostgreSQL transactions/RPCs where appropriate. A payment fulfillment operation should conceptually be: BEGIN lock payment IF payment already completed: return already_processed verify payment credit user insert ledger transaction mark payment completed COMMIT Do not allow the same payment to create credits twice. --- 10. STRIPE Inspect all Stripe code. The following is NOT acceptable in production: fake card fake receipt fake charge fake PaymentIntent sandbox fallback that credits real accounts Any endpoint similar to: /api/v1/stripe/pay-card must be removed, disabled, or replaced with a legitimate Stripe flow. Never accept raw card numbers or sensitive card details through SkillSwap. Use Stripe Checkout or PaymentIntents appropriately. Webhook handling must: 1. verify Stripe signature; 2. use the raw request body; 3. identify the payment; 4. verify the amount/currency/package; 5. be idempotent; 6. fulfill credits atomically; 7. record the event; 8. safely handle retries. --- 11.
